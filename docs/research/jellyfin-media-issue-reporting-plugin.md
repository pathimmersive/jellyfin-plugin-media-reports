# Turn hallway complaints into a triage queue

Yes. A Jellyfin 12.0 plugin can give your users a way to flag a movie, show, season or episode that won't play, plays wrong, looks bad or stutters, and give you an admin table to work those reports. One part needs care: getting the "Report" button in front of people. The closest thing that exists today is **Jellyfin-Enhanced's "Report Issue" button, which files into Seerr**. It works on the web client and the official Android and iOS apps. It does not reach the living-room TV apps (Android TV, Roku, Swiftfin, Infuse, probably Samsung), which is where most stutter actually gets noticed. It captures no playback diagnostics, and it limits you to Seerr's four issue types and two statuses. A custom plugin fixes all three gaps, and those gaps are the core of what you asked for. Build four things. The first is a phone-friendly report page hosted by the plugin and reached by QR code or sidebar link, which lists "playing now" and "just watched" from server-side session data, so a report about the TV can be filed from a phone. The second is an automatic snapshot of the client, device, play method and transcode reasons at submit time. The third is a dashboard triage page with grouping, six statuses and quick actions. The fourth is your own Discord or webhook alerts, because **Jellyfin 12.0 has no built-in notification system**. Budget **about 1 week for a spike, 5–6 person-weeks for a core loop you'd actually use, and about 14–15 person-weeks for a polished v1** with Radarr/Sonarr actions, re-linking across file upgrades, and optional Seerr forwarding. Maintenance runs **about 1–2 weeks a year**, mostly repairing the injected web button. If you already run Seerr, switch on Jellyfin-Enhanced's button tonight as a stopgap. Don't deploy Seerr only for this.

## Jellyfin-Enhanced plus Seerr supplies the button but not the diagnosis

Jellyfin itself will not do this. A 2024 request asked for the full feature you're describing: a mark-damaged checkbox, comments, client and user info, a timestamp for correlating logs, and admin notification. Maintainer nielsvanvelzen replied that Jellyfin is a home media server and problems should be raised with the family member nearby, and that plugins can only change the web UI, which isn't supported. A collaborator added that third-party software covers it ([GitHub discussion #11056](https://github.com/orgs/jellyfin/discussions/11056)). The maintainer's reply drew 1 upvote and 5 downvotes. That points to unmet demand, and it means a plugin is the only route. In August 2026 one user in that thread was emailing themselves reports by polling Jellyfin-Enhanced's *Reviews* API with a Python script. It worked on web and desktop but not on mobile ([same thread](https://github.com/orgs/jellyfin/discussions/11056)). That workaround shows the gap clearly.

**Seerr** is the most mature issue system. Overseerr and Jellyseerr merged into it in February 2026 ([ElfHosted](https://store.elfhosted.com/blog/2026/02/17/overseerr-and-jellyseerr-merge-into-seerr/)), and its latest release is **v3.5.0 (2026-09-28)** ([releases](https://api.github.com/repos/seerr-team/seerr/releases?per_page=5)). Its model is simple. There are **four issue types (Video, Audio, Subtitles, Other) and two statuses (Open, Resolved)**, plus a reopen event ([constants/issue.ts](https://raw.githubusercontent.com/seerr-team/seerr/develop/server/constants/issue.ts)). Each issue has season and episode targeting (0 means the whole series or season), a comment thread whose first comment is the user's note, and a relation to Seerr's own `Media` row rather than a Jellyfin item ([entity/Issue.ts](https://raw.githubusercontent.com/seerr-team/seerr/develop/server/entity/Issue.ts)). Three permission bits control who can create, view and manage issues ([permissions.ts](https://raw.githubusercontent.com/seerr-team/seerr/develop/server/lib/permissions.ts)). Seerr does notifications well: created, comment, resolved and reopened events go out through ten agents, including Discord, email, ntfy, Gotify, Pushover, Telegram, webhook and web push, with separate admin and user flags ([agents](https://api.github.com/repos/seerr-team/seerr/contents/server/lib/notifications/agents?ref=develop)). None of the 2026 release notes mentions Jellyfin 12, although v3.5.0 changed Jellyfin authorization headers ([releases](https://api.github.com/repos/seerr-team/seerr/releases?per_page=5)). **Seerr's 12.0 compatibility is unconfirmed.**

**Jellyfin-Enhanced** (n00bcodr, GPL-3.0) connects the two. It is the only way today to put a Report button inside Jellyfin clients. An opt-in setting adds "Report Issue" to item pages ("Report a problem (video, audio, subtitles or other) straight to Seerr"), and another adds a Seerr Issues section to its Requests page. Current builds target Jellyfin 12.x and 10.11.x ([Jellyfin-Enhanced](https://github.com/n00bcodr/Jellyfin-Enhanced)). The client side is a 1,117-line script that sends only `tmdbId`, media type, issue type 1–4, the message, and season and episode numbers. It sends **no client, device, play method or timestamp** ([issue-reporter.js](https://raw.githubusercontent.com/n00bcodr/Jellyfin-Enhanced/main/Jellyfin.Plugin.JellyfinEnhanced/js/jellyseerr/issue-reporter.js)). One research note left open whether the script calls Seerr directly. The other note settled it: requests go through Jellyfin-Enhanced's server controller, which enforces Seerr's `CREATE_ISSUES`/`VIEW_ISSUES` permissions, so the Seerr API key stays on the server ([JellyfinEnhancedController.cs](https://github.com/n00bcodr/Jellyfin-Enhanced/blob/HEAD/Jellyfin.Plugin.JellyfinEnhanced/Controllers/JellyfinEnhancedController.cs)).

Two other tools are useful as design contrasts. **Ombi** lets the admin define the issue categories, with suggestions such as Low Quality, Hardcoded subtitles, Wrong language and Incomplete video. It also has an optional **In Progress** status, so users can see someone is looking, and it auto-deletes resolved issues after N days ([Ombi docs](https://docs.ombi.app/settings/issues/)). **MediaDash** solves a different problem. It finds broken files proactively by test-playing each one at the start, middle and end, and offers Off, Detect only, Ask first or Automatic per fix, with dry-run as the default. It requires Jellyfin 10.11+ or 12.0+ and is not in the official catalog ([MediaDash](https://github.com/crackruckles/MediaDash)). It would catch a truncated file before anyone reports it. It would not catch "the subtitles are out of sync" or "it stutters on the Roku". Run it alongside a report plugin, not instead of one. I found no dedicated media-issue plugin for Jellyfin, but that search was web-only, not a GitHub code search ([prior-art notes](https://github.com/orgs/jellyfin/discussions/11056)).

| Need | Seerr + Jellyfin-Enhanced | Ombi | MediaDash | Custom plugin |
|---|---|---|---|---|
| Report from inside Jellyfin web/mobile | Yes (opt-in button) | No (separate app) | n/a | Yes |
| Report about something playing on a TV app | No | Separate app only | n/a | Yes, via phone page |
| Your own reason codes (stutter, wrong episode, quality) | No: 4 fixed types | Yes, admin-defined | n/a | Yes |
| Workflow beyond Open/Resolved | No | Adds In Progress | n/a | Yes |
| Auto-captured client, play method, transcode reasons | No | No | n/a | Yes |
| Proactive broken-file detection | No | No | Yes | Optional heuristics |
| Requires a second app | Seerr | Ombi | No | No |
| Items not on TMDb (home video, unmatched) | Can't report | Unverified | Yes | Yes |

## Only browser-based clients will ever show a Report button

Plugins can't add UI to Jellyfin clients through any supported API. The only route is injecting a script into the **server-hosted** jellyfin-web, using IAmParadox27's File Transformation plugin and n00bcodr's JavaScript Injector. The earlier ebook-reader research covered this in depth. It concluded that the maintainers rejected an official transformation hook in 2023, and that File Transformation 3.0 shipped for 12.0 on release day but has a history of breaking ([FT releases](https://github.com/IAmParadox27/jellyfin-plugin-file-transformation/releases); [PR #9095](https://github.com/jellyfin/jellyfin/pull/9095)). Injection therefore reaches only the clients that load the server's copy of jellyfin-web. The webOS app "hands off control to the hosted webUI" ([jellyfin-webos](https://github.com/jellyfin/jellyfin-webos)). The Tizen app builds jellyfin-web into its own package and must be rebuilt when the web client changes, so server-side injection almost certainly doesn't reach it ([jellyfin-tizen](https://github.com/jellyfin/jellyfin-tizen)). Jellyfin-Enhanced says its injected features reach the Android and iOS apps "through their embedded web UI" and Jellyfin Desktop "when it loads this server's web interface", while TV and other native clients get only server-side features ([Jellyfin-Enhanced](https://github.com/n00bcodr/Jellyfin-Enhanced)). The earlier ebook report listed the iOS app as unverified. This is the strongest evidence so far that it works, but test it on your own phone.

| Client | Shows an injected button? | Basis | Best entry point |
|---|---|---|---|
| Browser (desktop or phone) | Yes | Verified | Details-page button; sidebar link |
| Official Android app | Yes | Jellyfin-Enhanced docs | Details-page button |
| Official iOS app | Yes | Jellyfin-Enhanced docs; test it | Details-page button |
| LG webOS | Probably, but TV layout and remote only | README hand-off | QR card; button if it renders |
| Jellyfin Desktop / JMP | Only when loading the server UI | Jellyfin-Enhanced docs | Button or sidebar link |
| Samsung Tizen | Probably not (bundled web build) | Build steps | Phone page via QR |
| Xbox | Unknown | Not researched | Phone page via QR |
| Android TV / Fire TV, Roku, Swiftfin, Findroid, Streamyfin, Infuse, Kodi | No | Native clients ([bookreader README](https://github.com/mrozio1/jellyfin-plugin-bookreader)) | Phone page via QR |

I found no public data on which Jellyfin clients people use most ([JellyWatch](https://jellywatch.app/blog/best-jellyfin-clients-apps-2026)), but your own server can tell you. `SessionInfo.Client` records the client for every session, so the spike can count which clients your household uses. The design consequence holds either way. On most living-room setups the TV client can't show a button, so **the device-independent page is the product, and the injected button is a convenience**.

**The phone page** solves the "I'm on the couch watching the Roku" case, and it works because the server already knows what each user is watching. `ISessionManager.GetSessions` returns each session's `NowPlayingItem`, `PlayState`, `TranscodingInfo`, `Client`, `DeviceName` and `LastPlaybackCheckInPositionTicks` ([ISessionManager.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/MediaBrowser.Controller/Session/ISessionManager.cs); [SessionInfo.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/MediaBrowser.Controller/Session/SessionInfo.cs)). The page at, say, `/MediaIssues/Report` shows three lists after login. The first is **"Playing now on Living Room Roku"**. The second is **"Just watched"**, built from a plugin-side buffer of recent playback events plus the user's recently played items. The third is a search box. The user taps one, picks a reason chip, optionally types a note or nudges a timestamp, and submits. Users are never asked for an item ID or a season picker. The QR code can be static, printed on a card by the TV or shown on a help page, because the page works out the active session itself. Serve the page the way the ebook research established. The HTML is anonymous, the data endpoints require `[Authorize]`, and the page reuses the `jellyfin_credentials` token when opened from jellyfin-web, otherwise it signs in once. 12.0 rejects the legacy `X-Emby-Token` header and accepts only the `MediaBrowser` authorization header ([AuthorizationContext.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Jellyfin.Server.Implementations/Security/AuthorizationContext.cs)). Saved to a phone's home screen, it becomes a one-tap "report what I'm watching" button.

**Inside the web client**, add the button where Jellyfin-Enhanced does: in the details-page action row before the "more" button. Copy its approach, which listens for jellyfin-web's `viewshow` event and tries a cascade of selectors (`.detailButtons`, `.itemActionsBottom`, `[class*="ActionButtons"]`, `.mainDetailButtons` …) because 12.0's Modern and Legacy layouts differ ([issue-reporter.js](https://raw.githubusercontent.com/n00bcodr/Jellyfin-Enhanced/main/Jellyfin.Plugin.JellyfinEnhanced/js/jellyseerr/issue-reporter.js)). A second button in the video player overlay (OSD) would capture live position and stream indexes. Jellyfin-Enhanced already ships OSD buttons in 12.x ([repo tree](https://api.github.com/repos/n00bcodr/Jellyfin-Enhanced/git/trees/main?recursive=1)), but the overlay is the most fragile place to inject. Avoid the three-dot context menu, because its entries are built in minified code with no hook. From most to least stable: the plugin page, the details button, the OSD button, the context menu. A `menuLinks` sidebar entry in `/web/config.json` gives every web-based client a "Report a problem" link without per-page injection. It still needs File Transformation, or a hand edit that a Docker image update will overwrite.

Two other fallbacks are worth knowing about but not building first. A "magic playlist" would let native-client users add an item to a "Report a problem" playlist, which most native apps support, for the plugin to pick up. It carries no free text, and the 12.0 playlist events it would depend on are unverified. The plugin can also send a **`DisplayMessage`** to a TV session to confirm "Report received" or show a short URL. Server-side, `SendMessageCommand` targets any live session ([SessionManager.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Emby.Server.Implementations/Session/SessionManager.cs)), but which native clients actually display it is untested.

## The server already knows what was playing, but not that it stuttered

The plugin's biggest advantage over every existing option is that it runs inside the server that made the playback decision. At submit time, without any help from the client, it can snapshot several things. From `SessionInfo` it gets client name and version, device name, type and ID, and remote endpoint. From the session's `PlayState` and progress data it gets the item and media source, position, play method, and audio and subtitle stream indexes. The full `TranscodingInfo` adds video and audio codec, container, bitrate, width, height, framerate, `IsVideoDirect`/`IsAudioDirect`, **`HardwareAccelerationType` and `TranscodeReasons`** ([TranscodingInfo.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/MediaBrowser.Model/Session/TranscodingInfo.cs); [PlaybackProgressInfo.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/MediaBrowser.Model/Session/PlaybackProgressInfo.cs)). Server-side, `BaseItem.GetMediaStreams()` and `GetMediaSources()` add the file's own codec, resolution, HDR, audio-layout and subtitle-format details ([BaseItem.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/MediaBrowser.Controller/Entities/BaseItem.cs)). A report then reads "Alice, Roku Ultra, HEVC Main10 HDR → transcoding to H.264 on CPU, reason VideoCodecNotSupported, at 00:42:10". That is the context the 2024 requester wanted, and neither Seerr nor Jellyfin-Enhanced captures it ([issue-reporter.js](https://raw.githubusercontent.com/n00bcodr/Jellyfin-Enhanced/main/Jellyfin.Plugin.JellyfinEnhanced/js/jellyseerr/issue-reporter.js)).

There is a timing trap. Transcode info belongs to a live session, and whether it survives after playback stops is unverified. Many reports will come after the user gives up and stops, so the plugin should keep a **short in-memory ring buffer of each user's last-seen session state** from `PlaybackProgress` and `PlaybackStopped` events. "I just stopped watching" reports then still carry diagnostics. For web-client reports the injected script can add the browser user agent and player name, but the server-side data covers most of what matters. Redact `RemoteEndPoint` and absolute paths from anything a non-admin sees.

**Automatic detection is feasible, with one hard limit.** `ISessionManager` raises `PlaybackStart`, `PlaybackProgress` and `PlaybackStopped`. The stop event carries `PlayedToCompletion`, the position, client and device, and the session with its transcode info ([ISessionManager.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/MediaBrowser.Controller/Session/ISessionManager.cs); [PlaybackStopEventArgs.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/MediaBrowser.Controller/Library/PlaybackStopEventArgs.cs)). A plugin can compute several heuristics from these events:

- **Early abort:** stopped under about 60 seconds and not completed.
- **Restart loop:** two or more starts of the same item within a few minutes.
- **Stuck position:** the position stays unchanged while not paused.
- **Transcode fallback:** an unexpected transcode on a client that normally direct-plays.
- **Repeated mid-file stops:** several users stopping at the same timestamp, which points to a corrupt region.
- **Subtitle churn:** rapid subtitle-track changes early in playback.

Show these in a "Suspected problems" tab and use them to pre-fill the phone page ("Playback of X stopped after 12 s on Living Room Roku. Report a problem?"). Don't auto-file reports by default, because false positives will flood the queue. **Stutter is the limit.** None of the client-reported progress fields describes buffering, dropped frames or stalls ([PlaybackProgressInfo.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/MediaBrowser.Model/Session/PlaybackProgressInfo.cs)). The server only sees a stutter when the client gives up or the user complains. What the server can do is **explain** a reported stutter. A CPU transcode (`HardwareAccelerationType` none) of 4K HEVC at a high bitrate, or a forced subtitle burn-in in `TranscodeReasons`, accounts for most stutter reports. My own inference, untested, is that comparing `TranscodingInfo.CompletionPercentage` with playback position could show a transcoder that isn't keeping up. Playback Reporting's play-method strings like `Transcode (v:hevc a:direct)` show that this data is already logged in practice ([Jellyfin forum](https://forum.jellyfin.org/printthread.php?tid=13963)). Jellystat offers session logging but is in maintenance-only mode and doesn't document failure detection ([Jellystat](https://github.com/CyferShepard/Jellystat)).

This context matters more than usual in late 2026, because many "won't play" reports are not file problems. Jellyfin 12 requires an App field at login that Infuse doesn't send, so forced-transcode playback fails on 12.1, and InfuseSync is reported incompatible with 12.0 ([Firecore 12.1](https://community.firecore.com/t/login-crash-when-forcing-low-quality-remotely-jellyfin-12-1/60791.md); [InfuseSync](https://community.firecore.com/t/infusesync-for-jellyfin-v12-0/60185.md)). Grouping reports by client lets you see in seconds that every failing report came from one app. A button-only tool can't tell you that.

## A triage queue built on six statuses and provider IDs

**Where the admin table lives.** Classic `IHasWebPages` pages still work in the 12.0 React dashboard. jellyfin-web fetches the plugin's HTML and hands it to the legacy view loader, which runs inline scripts or a `data-controller` ES module ([ServerContentPage.tsx](https://github.com/jellyfin/jellyfin-web/blob/v12.0/src/components/ServerContentPage.tsx); [viewContainer.js](https://github.com/jellyfin/jellyfin-web/blob/v12.0/src/components/viewContainer.js)). `EnableInMainMenu = true` adds a sidebar entry under Plugins, and 12.0 now honours `MenuIcon` (a Material icon name such as `report_problem`). It ignores `MenuSection` ([PluginDrawerSection.tsx](https://github.com/jellyfin/jellyfin-web/blob/v12.0/src/apps/dashboard/components/drawer/sections/PluginDrawerSection.tsx); [JellyfinEnhanced.cs](https://github.com/n00bcodr/Jellyfin-Enhanced/blob/HEAD/Jellyfin.Plugin.JellyfinEnhanced/JellyfinEnhanced.cs)). The ebook research ruled these pages out for a user-facing reader because the listing is admin-only ([DashboardController.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Jellyfin.Api/Controllers/DashboardController.cs)). For an admin triage table that restriction is exactly right. The page's script calls the plugin's own `/MediaIssues/Admin/*` API, guarded by `[Authorize(Policy = "RequiresElevation")]` ([Policies.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/MediaBrowser.Common/Api/Policies.cs)). Playback Reporting (8 pages with per-page JS) and Intro Skipper (about 6.3k lines of bundled TypeScript UI) prove the pattern scales ([Playback Reporting Plugin.cs](https://github.com/jellyfin/jellyfin-plugin-playbackreporting/blob/HEAD/Jellyfin.Plugin.PlaybackReporting/Plugin.cs); [Intro Skipper web/src](https://github.com/intro-skipper/intro-skipper/tree/HEAD/web/src)). Bundle your own small UI. Don't try to borrow jellyfin-web's MUI. If the table outgrows the dashboard frame, the menu entry can link to a full-width page the plugin serves itself.

**Statuses, reasons and grouping.** Use **New → Investigating → Fixed / Won't fix / Duplicate / Can't reproduce**, plus a system status, **"Replaced – verify"**, described below. That takes Seerr's reopen event and Ombi's visible In Progress state and adds the outcomes a real queue needs. Make the reason codes admin-editable as Ombi does, and ship defaults that match your request: *won't play*, *plays incorrectly* (wrong episode, aspect, A/V sync), *poor quality*, *stutter/jitter*, *audio*, *subtitles*, *wrong metadata*, *other*. Store reports individually and group open reports by item (or provider ID) and reason within N days into one issue with a reporter count. Episodes roll up into season and series views, so "S2 has bad audio" from three people shows as one row. A workable private SQLite schema has three tables. `report` holds reporter, item, provider IDs, season and episode, path at report time, reason, text and a diagnostics JSON. `issue` is the group, with status, notes, resolution and timestamps. `event` is an audit log. That follows the private-database pattern Playback Reporting uses, because plugins can't add tables to `jellyfin.db` ([ActivityRepository.cs](https://github.com/jellyfin/jellyfin-plugin-playbackreporting/blob/master/Jellyfin.Plugin.PlaybackReporting/Data/ActivityRepository.cs)).

**Quick actions** come straight from stable server APIs. For v1, offer "open in Jellyfin" (`#/details?id=…&serverId=…`), path and stream details, refresh metadata, library rescan, and "mark fixed and notify" ([appRouter.js](https://github.com/jellyfin/jellyfin-web/blob/v12.0/src/components/router/appRouter.js); [ItemRefreshController.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Jellyfin.Api/Controllers/ItemRefreshController.cs); [LibraryController.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Jellyfin.Api/Controllers/LibraryController.cs)). Identify needs a search UI, so leave it for later ([ItemLookupController.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Jellyfin.Api/Controllers/ItemLookupController.cs)). For the **Radarr/Sonarr** loop ("this rip is bad, get another"), Radarr's v3 API looks up a movie by `tmdbId`, deletes a `moviefile/{id}`, and takes search commands at `/api/v3/command`. Sonarr's does the same with `tvdbId` and `episodefile/{id}` ([Radarr OpenAPI](https://raw.githubusercontent.com/Radarr/Radarr/develop/src/Radarr.Api.V3/openapi.json); [Sonarr OpenAPI](https://raw.githubusercontent.com/Sonarr/Sonarr/v5-develop/src/Sonarr.Api.V3/openapi.json)). Call them from the server so API keys never reach the browser, as Jellyfin-Enhanced's `ArrUrlGuard` does ([JE Helpers](https://github.com/n00bcodr/Jellyfin-Enhanced/tree/HEAD/Jellyfin.Plugin.JellyfinEnhanced/Helpers)). Keep "delete file and re-search" behind a confirmation and off by default. The exact command payload names (`MoviesSearch`, `EpisodeSearch`) are not in the specs and come from background knowledge.

**Keeping reports attached across file replacement** is the subtle part, and Radarr upgrades cause it. A Jellyfin item ID is an MD5 of the type name plus the path ([LibraryManager.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/Emby.Server.Implementations/Library/LibraryManager.cs)). Overwriting a file under the same name keeps the ID. An upgrade that renames the file, which is normal when the naming template includes quality or codec, creates a new item, and the old one disappears on the next scan. So store provider IDs (TMDb, TVDb, IMDb), series, season and episode numbers, and the original path alongside the item ID ([IHasProviderIds.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/MediaBrowser.Model/Entities/IHasProviderIds.cs)). Subscribe to `ILibraryManager.ItemRemoved` and `ItemAdded` ([ILibraryManager.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/MediaBrowser.Controller/Library/ILibraryManager.cs)), which the Webhook plugin already does ([ItemDeletedNotifierEntryPoint.cs](https://github.com/jellyfin/jellyfin-plugin-webhook/blob/HEAD/Jellyfin.Plugin.Webhook/Notifiers/ItemDeletedNotifier/ItemDeletedNotifierEntryPoint.cs)). On removal, mark open reports "orphaned". On add, re-point orphans with matching provider IDs and set them to **Replaced – verify**, which turns a Radarr upgrade into a one-click "confirm and tell Alice it's fixed". A scheduled reconcile task catches anything the events miss. Unmatched items without provider IDs should be flagged for manual linking, not auto-linked.

**Notifications must be built in.** Core notifications were removed after 10.9 and moved to the Webhook plugin ([discussion #11664](https://github.com/jellyfin/jellyfin/discussions/11664)). At v12.0 there is no notifications controller or manager in the server. The Webhook plugin's notifiers are fixed classes for core events, and nothing uses its `Generic` type, so another plugin can't feed it custom events ([Webhook notifiers](https://github.com/jellyfin/jellyfin-plugin-webhook/tree/HEAD/Jellyfin.Plugin.Webhook/Notifiers)). For **you**, the plugin should post to a Discord webhook URL and a generic JSON webhook (which covers ntfy, Gotify, Home Assistant and n8n), batched so three reports in an hour arrive as one message. It should also write an `IActivityManager` entry so the report appears in the dashboard activity feed with no setup ([IActivityManager.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/MediaBrowser.Model/Activity/IActivityManager.cs)). Optionally, it can toast your online admin sessions via `SendMessageToAdminSessions` ([ISessionManager.cs](https://github.com/jellyfin/jellyfin/blob/v12.0/MediaBrowser.Controller/Session/ISessionManager.cs)). For the **reporter**, Jellyfin's only built-in channel is `DisplayMessage` to a live session. jellyfin-web shows it as a toast when a timeout is set and as a blocking alert otherwise ([serverNotifications.js](https://github.com/jellyfin/jellyfin-web/blob/v12.0/src/scripts/serverNotifications.js)), and it fails if the user isn't connected. The durable channel is a "My reports" list on the phone page plus an unread badge that the injected web script checks on load.

## Build a lean plugin, and forward to Seerr only if you already run it

**Adopt first if Seerr is already in your stack.** Enabling Jellyfin-Enhanced's button and Seerr's Issues section costs an evening. It immediately covers web, Android and iOS users with notifications to both you and the reporter, and it shows you how much reporting your household actually does. Its ceilings are permanent, though: no TV-client path, four types, two statuses, no diagnostics, no reports on media Seerr doesn't know, and a dependency on Seerr's still-unconfirmed 12.0 support. **If you don't run Seerr, don't deploy it for this.** You'd add a second app, user import and permission grants just to get a worse fit than the plugin.

**Build a custom plugin with local storage as the source of truth**, and treat Seerr as an optional outbound connector. Seerr's API supports forwarding. `POST /api/v1/issue` takes `mediaId`, `issueType`, `message`, `problemSeason` and `problemEpisode`, and an admin API key plus an `X-API-User` header files it on the user's behalf ([routes/issue.ts](https://github.com/seerr-team/seerr/blob/HEAD/server/routes/issue.ts); [middleware/auth.ts](https://github.com/seerr-team/seerr/blob/HEAD/server/middleware/auth.ts)). One note found that `seerr-api.yml` omits the season and episode fields. The route source reads them, so the published spec is just incomplete ([seerr-api.yml](https://raw.githubusercontent.com/seerr-team/seerr/develop/seerr-api.yml)). The catch is that `mediaId` is Seerr's internal row ID, and Seerr returns 404 for titles it hasn't synced. The connector therefore needs a TMDb → Seerr media lookup, a Jellyfin → Seerr user mapping (not yet researched), and a graceful "kept locally only" fallback.

The estimates below are judgement-based. They are anchored on comparable plugins (Playback Reporting is about 5.7k lines, Webhook about 5.5k, Jellyfin-Enhanced about 150k), not on measured effort. They assume one experienced .NET and web developer who is new to Jellyfin internals ([line counts from the plugin repos](https://github.com/jellyfin/jellyfin-plugin-playbackreporting)). The research notes' work-package table sums to about 14.5 person-weeks for a polished v1, while their summary quoted 10–15 and "9–12". The 9–12 figure assumes one optional package is dropped (Seerr connector, identify UI or dual-ABI packaging). The phasing below reconciles them. At ten hobby hours a week, phase 1 takes roughly five months of calendar time. Phase 1 alone already beats both the casual status quo and the Seerr route on your stated needs. The injected button is deliberately phase 2, because it carries the most maintenance and adds the least for TV-heavy households. **Infrastructure is shared with the ebook reader.** Both plugins need the same net10/`targetAbi 12.0.0.0` shell copied from Playback Reporting, an anonymous-HTML/authorized-API controller pattern, the `jellyfin_credentials` token lookup isolated in one module, private SQLite in the plugin data folder, a self-hosted `manifest.json` with CI, and an optional File Transformation injection module ([Playback Reporting csproj](https://github.com/jellyfin/jellyfin-plugin-playbackreporting/blob/master/Jellyfin.Plugin.PlaybackReporting/Jellyfin.Plugin.PlaybackReporting.csproj); [JE manifest.json](https://github.com/n00bcodr/Jellyfin-Enhanced/blob/main/manifest.json)). Put both in one repository with a shared source project compiled into each DLL, not a shared runtime assembly, which would risk load conflicts between plugins. Publish both from one manifest. Whichever plugin you build second should save roughly a week of shell and packaging work, by my estimate.

### Risks and what remains unverified

The injected button depends on jellyfin-web DOM that changes between releases, and on File Transformation, which crashed 10.11.6 at startup in its 2.5.4 release ([FT #46](https://github.com/IAmParadox27/jellyfin-plugin-file-transformation/issues/46)). Keeping the phone page as the primary entry point limits that risk. Jellyfin 12.x client regressions will produce "won't play" reports that are really client bugs. The diagnostics make those visible, but expect some noise. Native clients' playback reporting reliability is anecdotal, so heuristics may misfire on Roku and third-party apps. Whether 12.0's backup includes plugin data folders is still unverified, so add an export endpoint. Several facts in the notes were read from jellyfin `master`, not the `v12.0` tag. ### First step: a one-week spike on your own TV

Build a net10 plugin with three pieces. The first is a hosted service that subscribes to `PlaybackStart`, `PlaybackProgress` and `PlaybackStopped` and keeps the per-user ring buffer. The second is an anonymous `/MediaIssues/Report` page that signs in, lists "playing now" and "just watched" for that user, and posts a report with the snapshot into SQLite. The third is a bare dashboard page listing the rows. Then start something that forces a transcode on your main TV client, open the page on your phone via a QR code, and file a report while it plays. Stop playback and file a second report to see what diagnostics survive. Send a `DisplayMessage` to each TV client to see which ones show it. Log `SessionInfo.Client` for a week to learn which clients your household actually uses. Finally, diff the master-read event and DTO files against the `v12.0` tag. Those results decide whether phase 2's injected button is worth building at all.

## Conclusion

The research changes what this plugin actually is. The obvious framing is "a Report button", and that is the part existing tools already do and that can't reach your TV. The real value is server-side: Jellyfin already knows who was watching what, on which device, and why it transcoded, and nobody captures that at the moment someone says "it's stuttering". A report that arrives with that snapshot changes your job from interviewing the reporter to reading a row. Combined with client grouping, it also tells file problems apart from client problems, which matters while 12.x client compatibility is still settling.

The phone-first design also covers the maintainers' objection. Their view was that a household problem should be raised with the person nearby. A report page on the phone in the user's hand is that same conversation, with the server supplying the details. It needs no client cooperation, survives jellyfin-web churn, and shares most of its infrastructure with the ebook reader. Building it first gives you the plugin skeleton both projects will use.
